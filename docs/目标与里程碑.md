## 开发目标

批量媒体转码的「交付出口」（对标 Media Encoder 核心工作流）：队列
管理、预设体系（内置 + 自建 + 收藏）、输出命名规则、批量交付。锻在
集群里的角色：**冶「成器」的第一验证场**——冶（炼材）提供底层编解码
与封装，锻在其上构建转码产品（ye/README 既有表述）。

## 状态快照

- M0 骨架、M1 转码闭环、M2 四区界面：已完成（各附单测）。
- M3 打包发布实跑：**进行中**——提交停在打包配套（权限、CI 补

## 引擎线：ffmpeg → 冶（新增，对齐 ye/docs/integration.md）

当前引擎是随包分发的 ffmpeg 二进制（fetch-ffmpeg，约 +170MB）。
集群既定方向是冶以 Cargo 依赖进程内服务锻。分步迁移，**不阻塞
队列功能演进**：

- **D0（现状）**：ffmpeg 承担全部转码（probe/解码/编码/封装）。
- **D1 probe 换冶**（冶 M1 的 mp4 落地后）：队列页素材信息走冶的
  进程内 probe，与剪共用 probe 缓存（integration.md）。
- **D2 转码引擎换冶**（冶 M3 处理图 + CLI、M4 编码后）：
  demux → decode → filter → encode → mux 走冶——**冶 M3 的准入
  条件即「锻完成一次转码」**，届时本项就是那条验收。ffmpeg 从
  随包分发降为可选，安装体积回收约 170MB。
- **D3 硬件加速**（冶 M5 后）：NVENC / D3D11VA 接入即锻的硬编
  能力线。
- 每步保留 ffmpeg 回退开关；D2 落地后锻成为冶与 ffmpeg 的天然
  对照基准（同素材双引擎输出比对）。

## 集群对齐

- 外壳依赖坊（AppShell/DockPanel 已接入）；锻与剪共享 ffmpeg
  sidecar 定位方案（三档 env → binaries → PATH，移植自剪）。
- 冶的 M3/M4/M5 里程碑以锻的真实任务为验收，锻的引擎线以冶的
  里程碑为解锁条件——两线互为准入。
