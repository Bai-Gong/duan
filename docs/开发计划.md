## 定位与边界

### 产品定位

百工·锻 MVP 是一个真实可用的批量转码闭环 Windows 桌面应用：多选/拖入/文件夹导入音视频素材，ffprobe 探测元数据，从内置、自建或收藏预设中套用一个（可逐项弹导出设置并另存为预设），按默认输出目录+「文件名.预设名.扩展名」命名规则（冲突自增）生成输出路径，一键开跑队列后由后台 ffmpeg 逐项串行转码，队列表实时显示进度条与状态色标，右侧「正在编码」面板显示当前项缩略图与大号进度，点选队列项弹出预览监视器查看源信息与代表帧，完成后可直接打开产物或所在文件夹。

### 明确不做（MVP 边界）

- 监视文件夹、收录/代理工作流、ProRes/DNx/AV1/HDR、字幕嵌入、入出点裁剪、LUT/响度统一（均为产品分析.md:17 后置清单）
- 多任务并行与暂停/恢复（提供取消、跳过、重排，串行单 worker）
- 队列持久化与崩溃恢复（预设与收藏持久化，队列重启即清）
- 完整源/输出画面对比预览（保留源元数据+代表帧+打开输出）
- 非 Windows 平台打包与专属图标（沿用 Tauri 默认图标集）
- 系统级通知（完成态在应用内醒目反馈）

## 技术决策及理由

### 决策 1：ffmpeg 获取与调用（最重要决策）

**决策**：运行时定位完整移植 jian 三档（BJ_FFMPEG_DIR → src-tauri/binaries → 系统 PATH，OnceLock 缓存）；开发期用自 jian 移植的 scripts/fetch-ffmpeg.mjs 下载 BtbN win64-gpl（非 shared）到 src-tauri/binaries/——本机 ffmpeg 不在 PATH，该脚本是开发主路径；脚本增加令牌支持：读 GITHUB_TOKEN/GH_TOKEN 环境变量，有则在查询 latest release 的 fetch 上带 Authorization header，无则维持匿名（本地零负担）；CI 的 qa/release 打包 job 在跑脚本前先跑 fetch 步骤并透传 env GITHUB_TOKEN: ${{ github.token }}（Actions 自带 token 的 API 额度为 1000 次/时/仓库——GitHub 官方 rate-limit 文档本轮核实，Enterprise Cloud 才是 15000，5000/时是个人 PAT 额度；单次打包仅需 1 次 release 查询，远够）。分发走 tauri.conf.json bundle.resources 把 binaries/* 映射进安装目录（Windows 资源目录=exe 同级，与 sidecar_dirs() 的 exe.parent()/binaries 查找重合，jian/ffmpeg.rs:69-80）；resources 映射与 CI fetch 步骤必须同一提交落地（否则 runner 上无 binaries、glob 空匹配可能使打包失败——空匹配行为未实测，见风险）。脚本本体（纯复制+token 增强，无 Rust 依赖）提前到 M0 创建并实跑下载验证；「用真实样片跑通转码」随模块2（M1 首项）。

**理由**：jian/ffmpeg.rs:38-58 三档定位已落地零风险照搬；匿名限流不是理论值——本轮实测 curl https://api.github.com/repos/BtbN/FFmpeg-Builds/releases/latest 返回 HTTP/1.1 403 rate limit exceeded、X-RateLimit-Remaining: 0（60/时额度耗尽），GitHub 托管 runner 出口 IP 共享更易撞墙，jian 脚本 :70-72 只带 User-Agent 无 Authorization 口，必须补；下载本体走 browser_download_url 不占 API 限流，带 token 只需护住查询那一次。不选 externalBin+plugin-shell：需目标三元组重命名并引入 shell 插件，jian 先例是裸 std Command+绝对路径。代价：resources 落位匹配是推断，集群无先例（jian release.yml:4 自认 sidecar 打包未落地），M3 首次 release 实测，退路 externalBin。安装包约 +170MB，MVP 接受。

### 决策 2：执行与进度模型

**决策**：前端纯函数 buildTranscodeArgs 生成完整 ffmpeg args（含 -y -progress pipe:1 -nostats 与输出路径收尾），Rust 侧 run_transcode(app, job_id, args, out_path, total_us) 逐行读 stdout 的 out_time_us、按 jobId 发 transcode-progress 事件；stderr 单开线程收集防管道塞死、失败回传尾部 500 字符——照搬 jian run_export（ffmpeg.rs:161-207）；新增取消：static KILL: Mutex\<HashMap\<String,Child\>\> 句柄表 + cancel_transcode(job_id)。取消后的非零退出按 jian 语义会走 Err 分支（ffmpeg.rs:197-205），区分责任在 runner 侧标记（见模块5），Rust 不做特殊处理。

**理由**：「前端生成 args、Rust 只执行与报进度」使参数翻译成为可单测纯函数（jian buildExportArgs+测试即样板）；jian ExportProgress 无 id（ffmpeg.rs:24-27）、run_export 无取消口，锻是队列产品，进度必须带 jobId 路由、取消/跳过是产品分析.md:25 明确交互。kill 后退出码非零属正常语义，在调用方区分「用户取消」与「真失败」比在 Rust 侧猜更可靠。

### 决策 3：队列模型

**决策**：MVP 单 worker 严格串行（并行编码是产品分析.md:17 后置项）；状态机 waiting/running/done/failed/canceled/skipped；提供取消/跳过/上移下移，「暂停」后置（本质=kill+重跑，以取消代替）；zustand 管理队列，localStorage（persist）只存自建预设+收藏+默认输出目录，队列不持久化。

**理由**：串行使单 jobId 进度路由、取消句柄表、失败语义最简，先闭环再并行化；预设是复用根基（产品分析.md:13 必备③）故进 MVP 并持久化，队列持久化涉及崩溃恢复语义，砍出边界。
